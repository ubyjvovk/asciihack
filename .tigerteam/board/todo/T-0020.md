## Goal
Resizing the terminal leaves stale fragments until the next keypress,
game event or `Ctrl+L`. `Screen`'s constructor registers the only
`TermIO.onResize` callback and just calls `invalidate()`; the `App` never
learns about the resize, so nothing recomposes or paints. Make a resize
recompose and paint at once (PM reproduced it in tmux: shrink 215×68 →
120×40 left the old map fragments and no status rows; `Ctrl+L` fixed it).

## Context
- `src/term/tty.ts` (`onResize` stores a single callback), `src/term/screen.ts`
  (`Screen` constructor: `term.onResize(() => this.invalidate())`),
  `src/ui/app.ts` (compose + `screen.paint`; `Ctrl+L` path is the model:
  invalidate then repaint).
- Fix: let `TermIO.onResize` accept multiple listeners (keep the `off`
  bookkeeping in `tty.ts` `restore()`), and have `App` subscribe: on
  resize → `screen.invalidate()` → recompose for the new `columns/rows`
  → `paint` immediately (the too-small banner path when < 80×24 also
  goes through here). Debounce nothing; a resize storm is just a few
  full repaints.
