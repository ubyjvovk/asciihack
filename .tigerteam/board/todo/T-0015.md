## Goal
Three small things the PM saw while playing classic mode (T-0004) that
make the game feel off; none blocks play, all are cheap.

## Context
- **yn default shows as `[]`.** `YnOverlay` (src/ui/overlays.ts ~265)
  prints `` [${String.fromCharCode(def)}] `` whenever `def` is non-zero;
  "Really save?" arrived with a control-character default so the box
  read `Really save? yn []`. Print the default only when it is a
  printable ASCII character (0x21–0x7e), and format the prompt like
  tty does: `Really save? [yn] (n)`.
- **Menu cancel sends "nothing selected", not "cancelled".**
  `NethackSession.answer({kind:'menu', selected: []})` serialises `ret 0`;
  the protocol (`docs/architecture.md` §3.3 `select_menu`) has `ret −1`
  for a cancelled menu and NetHack behaves differently for the two on
  some prompts. Add `{kind:'menu', cancelled: true}` to the `Answer`
  union → `{id, ret: -1}` (no `selected`), and make `MenuOverlay` send it
  on ESC (Enter with nothing picked stays `ret 0`). Document both in
  `docs/engine.md`.
- **Final `--More--` after the bridge has gone.** After `S`/`y` NetHack
  prints "Saving..." with a blocking message display, then exits; the
  App waits for a keypress on a `--More--` whose game is already over.
  When the session emits `exit` while a `display`/`more` overlay is the
  only thing pending, dismiss it and leave immediately (keep the pause
  when the bridge is still alive — death messages and DYWYPI need it).
  Also make sure the process exits within 500 ms of `exit` even if some
  timer/stdin listener is still registered (`tty.ts` leave path).

Item 3 does not work in the live game (PM playtest: after `S`, `y` the
process is still waiting 4 s later), and the reason is my premise, not your
code: NetHack's `dosave()` (`nethack/src/save.c` lines 52–65) does
`pline("Saving...")` → `display_nhwindow(WIN_MESSAGE, TRUE)` "to make sure
they see the Saving message" → `exit_nhwindows("Be seeing you...")` →
`nh_terminate()`. That blocking display is a call the bridge waits on, so
NetHack cannot exit until we answer it — the `exit` event can never arrive
while the `--More--` is pending. Keep your exit-time guard (harmless), but
implement the real fix:

- In the App, when a blocking `display` request for the **message window**
  arrives and the newest message since the previous key request is exactly
  `Saving...` (NetHack's literal), paint the frame once and answer
  `dismiss` immediately, without waiting for a key. Every other blocking
  message display keeps pausing (death, DYWYPI, level change).
- In the session, `exit_nhwindows(str)` with a non-null string is appended
  to `messages` (it is "Be seeing you...") — today it is a no-op case.
- In `src/cli.ts`, after `app.leave()` restores the terminal, print the
  last two messages (e.g. `Saving...  Be seeing you...`) on one line to
  stdout so the player gets the farewell tty shows, then exit with the
  bridge's code.

Tests (only these, replace the exit-during-`--More--` one if it no longer
means anything): `auto-dismisses the Saving... --More--` (feed
`raw_print "Saving..."` then `display_nhwindow(msgwin, true)` → the
session receives `dismiss` with no key event) and `a blocking display after
an ordinary message still waits` (feed `"You die..."` + blocking display →
no answer until a key). Manual: `S`, `y` in classic mode exits with no
