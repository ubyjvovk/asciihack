## Goal
In the third-person view the natural thing is to click where you want to go.
Add it: click a cell, and if a walkable path through **known** terrain
exists, walk it.

## Context
- **The sources are vendored in-repo at `vendor/afterburn/` (read-only).**
- Two halves, keep them apart:
  1. **Picking** (`web/src/gpu/pick.ts`): turn a click into a map cell.
     The GL canvas has `pointer-events: none` (docs/web.md "WebGL viewport")
     so the DOM terminal keeps focus — do **not** change that. Listen on the
     existing `<pre id="term">` instead, take the event's client
     coordinates relative to the canvas rectangle, and unproject onto the
     **floor plane `y = 0`** using the viewport's live camera. Export a pure
     `cellUnderRay(origin, dir)` so the maths is testable in node without a
     renderer; the impure part reads the camera and calls it.
  2. **Travel** (`src/ui/travel.ts`): a breadth-first search over the
     session's remembered map from the hero to the target. Passable = the
     `isSolid` test already used by the renderers, and **known cells only**
     (`kindAt !== 'unexplored'`) — never path through territory the player
     has not seen. Diagonals allowed, but not squeezing between two
     diagonal walls. Returns the cell sequence, or null when unreachable.
- **Sending the moves, decided.** Convert each step to its vi-key and send
  them one at a time through the existing `sendKey` path, **one key per
  frame at most**, stopping early if: the hero does not end up where the step
  expected (something blocked or interrupted), the message line changes, or
  any key is pressed. NetHack is turn-based and can interrupt for a hundred
  reasons — a queued burst that ignores the result would walk the player into
  a monster. Do **not** use NetHack's own `_` travel command; driving its
  cursor prompt over the bridge is a bigger and more fragile job.
- A click on an unreachable or unknown cell does nothing (no beep, no
  message) — silence is the right feedback for "no path".

Two separate defects.

### 1. `cellUnderRay` has no validity check

`{x: 5, y: -86}` is off the map. That is the classic ray/plane failure: when
the ray is near-parallel to `y = 0` (a click near or above the horizon) the
intersection parameter blows up and the hit lands arbitrarily far away.
Reject it instead of returning it:

- if the ray's `dy` is ~0 (say `|dy| < 1e-4`), or the intersection is
  **behind** the camera (`t <= 0`), or lands further than a sane bound
  (use **40 cells**, past which nothing is on screen anyway) → return `null`.
- a cell outside `0 ≤ x < map.width`, `0 ≤ y < map.height` → `null`.

Add this to the pure function so it is testable, and extend the existing
`cellUnderRay hits the floor plane under the cursor` case or add
**exactly one** new case named
`cellUnderRay returns null for a ray that misses the floor`.

### 2. Nothing moves, even for a good pick

(4, 7), (6, 7) and (5, 6) are all adjacent to a hero standing at (5, 7), so
at least one is walkable and trivially reachable — yet the camera never
moved, over four clicks and ten seconds. So the failure is downstream of the
pick: `findPath` returning null, or `traveler.start()` never sending a key.
Find out which. Likely suspects, in the order I would check them:

- a coordinate mismatch between `session.hero` and the cell `pickCell`
  returns (an x/y swap or an off-by-one would make every path fail);
- `findPath`'s passability test rejecting the hero's *own* start cell, or
  requiring `kindAt` values that the live session reports differently from
  the synthetic fixtures the tests use;
- the traveler's per-frame tick never running, or its first step being
  cancelled immediately by the "did the hero end up where the step expected"
  guard before the move resolves.

**Give yourself an instrument first.** Add to the debug handle —
`window.__asciihack` — a `travel` object reporting the last pick, the last
path length and the traveler's state. Tonight's ortho bug took three
attempts until `debugInfo()` stopped lying about which camera was live; the
same move applies here. Then the failing step is one page-console call away
instead of a guess.

### Rework findings

Two independent defects, one per section of the review, plus a third I
found while chasing (2) that would have kept the fix silent even after the
picker was corrected.

**1. `cellUnderRay` had no validity check.** A near-parallel-to-floor ray
(clicks near the horizon in the third view) pushed `t = -origin.y / dir.y`
past any reasonable bound and produced picks like `{ x: 5, y: -86 }`.
Added, in `web/src/gpu/pick.ts:53`:
- `|dir.y| < 1e-4` (`DY_PARALLEL_EPS`) → null
- `t ≤ 0` or `t > MAX_HIT_DIST_CELLS` (= 40) → null
- optional `bounds: { width, height }` — hit outside `[0, width) × [0, height)`
  returns null so `findPath` never sees an off-map coordinate

**2. Nothing moved even for a good pick — root cause: NetHack's main input
path is `nh_poskey`, not `nhgetch`.** `nethack/src/cmd.c:5247`
(`readchar_core`) calls `nh_poskey(x, y, mod)`; the bridge relays that as
a `PosRequest` (`bridge/nh-bridge.c:933`), so `session.pending.kind` is
`'pos'` during ordinary play. The v1 traveler aborted on anything other
than `'key'` — so every click aborted silently on the first `tick`.
`sendKey` (`src/ui/view3d.ts:189`) already handles both. Fix
(`web/src/main.ts:378`): accept `'key'` and `'pos'`; reserve the interrupt
for menus / yn / getlin / display. That is the single change that makes
the hero actually walk.

**3. Load-bearing `updateMatrixWorld(true)` in `GlViewport.pickCell`
(gl-viewport.ts:338).** `Raycaster.setFromCamera` reads the origin from
`camera.matrixWorld`; `position.set` and `lookAt` only mutate
`position`/`quaternion`. When the GPU path draws the frame, GlViewport's
legacy `this.camera` / `this.orthoCamera` are never handed to
`WebGLRenderer.render`, so `matrixWorld` stays at construction identity
and the ray comes from the world origin. Forcing the update in both
branches is what stabilises the pick coordinates the PM tabulated in the
rework note.

**Debug handle** (per the rework's instruction to instrument first):
`window.__asciihack.travel.debug.lastPick`, `.lastPathLength`, and
`window.__asciihack.travel.state()` (path length, `expectedNext`,
`msgSnapshot`, current `pending` kind, and `lastAbortReason` — one of
`'not-key-or-pos' | 'message-changed' | 'no-hero' | 'blocked' |
'no-step-key' | 'user-key' | 'new-path' | null`). A stuck walk is now one
console call away.

## Rework (attempt 3) — narrowed to one step

Picking is **fixed and verified**: the validity check works and
`pickCell` returns sane in-bounds cells. `findPath` is **working**: it
returns a 1-step path to an adjacent cell. The `nh_poskey` finding was real.
Everything up to "send the key" is done — **do not touch it**. What remains

**The traveler sends its key and then hangs forever.** Driven from a live
game, clicking an adjacent cell, sampling
`window.__asciihack.travel.state()`:

| when | state |
|---|---|
| before click | `pathLength 0, expectedNext null, msgSnapshot 0, pending "pos"` |
| +100 ms | `pathLength 0, expectedNext {24,8}, msgSnapshot 1, pending "pos"` |
| +600 ms | *identical* |
| +2 s | *identical* |
| +5 s | *identical* |

And the terminal's `textContent` is **byte-identical** across the click, so
the hero never moved and NetHack never redrew.

Read that carefully, because it says a lot:

- `pathLength` went to 0 and `expectedNext` was set, so the traveler did pop
  its single step and believes it sent the key.
- `msgSnapshot` moved 0 → 1, so *something* came back from NetHack.
- `pending` stays `"pos"` the whole time — NetHack is still asking.
- `lastAbortReason` stays `null` **forever**. Nothing gives up.

So the reply is not being accepted as a move. Two things to fix:

1. **Make the key actually take effect when `pending.kind === 'pos'`.**
   Check what the bridge's `PosRequest` reply shape really is
   (`bridge/nh-bridge.c`, and the `RetMsg` types in
   `src/engine/protocol.ts`) and what `nh_poskey` does with each field.
   A vi-key sent in the wrong field is accepted and discarded — which
   matches `msgSnapshot` moving while the map does not. Compare against
   what the *keyboard* path sends for the same move: pressing `h` plainly
   works today, so **diff your reply against that one** — that is the
   fastest route to the answer, and say in the report what differed.

2. **Never hang.** A traveler that waits forever with no abort reason is
   worse than one that gives up. Add a timeout: if `expectedNext` has not
   been reached within **1.5 s**, abort with reason `'timeout'`. Then a
   future failure shows up in `state()` instead of wedging silently.
