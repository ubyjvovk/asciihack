## Goal
Movement reads as jerky. The **camera** is already smoothed — `dampPose` runs
every frame (`gl-viewport.ts`) — but the **hero is not**: `poseFor` returns
the cell centre the instant NetHack reports a move, so the avatar teleports a
whole cell and the camera spring then lurches after it. Afterburn's
characters glide. Make ours glide.

## Context
- **The sources are vendored in-repo at `vendor/afterburn/` (read-only).**
  `~/afterburn` is not visible in the worker container.
  `vendor/afterburn/src/models/body.js` holds their character rig and the
  damping helpers their movement uses — read it for the feel, not to copy
  wholesale (their character moves continuously; ours is turn-based).
- `src/ui/view3d.ts`: `poseFor(hero, yawRad)` → `{ x: hero.x + 0.5, y:
  hero.y + 0.5, yaw }`. Every caller gets an instant jump on a cell change.
- **The design, decided.** Add a small stateful smoother beside `poseFor`:
  `createPoseSmoother({ cellSeconds })` returning `update(hero, yawRad, dt)`
  → `Pose`. It holds the displayed position, and each frame eases it toward
  the true cell centre. Numbers:
  - **`cellSeconds = 0.12`** — one cell in 120 ms, matching the existing
    turn animation so a move and the turn that accompanies it finish
    together.
  - Ease with the **same exponential damper** the camera uses
    (`dampPose`-style, framerate independent: `1 - exp(-dt / tau)`), not a
    linear lerp — a spring that never quite arrives reads better than one
    that stops dead.
  - **Snap, do not glide, when the jump is more than 1.9 cells.** Level
    changes, teleports and `<`/`>` must not send the avatar skating across
    the map. Test this.
- Yaw already animates (the 120 ms turn in `FpsMode`); leave it alone.
- Wire it in the browser's render loop only. The terminal fps mode renders
  from the true cell and must be untouched — its existing tests passing
  unchanged is the proof.
