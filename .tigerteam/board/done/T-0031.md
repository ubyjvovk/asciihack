## Goal
The point of the browser build: render the dungeon with AsciiCity's real
renderers. Build a three.js scene from the session's map (walls as brick
boxes, flagstone floors, doors, stairs, sprites as billboards textured
with NetHack's tile art), a first-person camera that follows the hero and
facing, a lantern light and fog, and run it through the vendored
`StyleRenderer` so the frame is drawn by the `amber`/`ascii`/`gloom`/
`matrix`/… fragment-shader styles. The WebGL canvas sits under the DOM
terminal's viewport rectangle; the HUD (message line, status, minimap,
compass, menus) stays in the `<pre>` grid from T-0030.

## Context
- Vendored, do-not-edit: `web/src/asciicity/render/` — `style.ts`
  (`RenderStyle`, `STYLE_PRELUDE`, `STYLE_ORDER`), `post.ts`
  (`StyleRenderer`: owns the low-res target and swaps styles; `styleGrid`),
  `scene.ts` (`makeRenderer`, `makeScene`, `makeCamera` with AsciiCity's
  constants), `styles/*.ts` (`STYLES` registries), `crt.ts` (optional
  scanline overlay). Read `web/src/asciicity/README.md` and AsciiCity's
  conventions: pixel ratio 1, the style decides cell size (`cellW`/`cellH`)
  and sub-samples; the target is `cols·subX × rows·subY`.
- Session/model: `docs/engine.md`, `src/model/types.ts` (`LevelView`,
  `MapCell`, `CellKind`, `Sprite`, `Tile`), `src/ui/view3d.ts`
  (`FACINGS`, `spritesFromMap` with tiles from T-0026 — reuse it), the
  fps mode's facing/yaw (T-0007/T-0024: `FpsMode` owns `facing`, `yaw`,
  `vFovDeg`). Coordinates: architecture.md §7 — map `x` east, `y` south;
  three.js: use `x` east, `z` south, `y` up (AsciiCity's convention).
- `web/src/gl/scene-builder.ts` (pure where possible): from a `LevelView`
  build/refresh geometry incrementally — one merged `BufferGeometry` per
  material for walls (unit cubes for `isSolid` kinds except
  `unexplored`), floors (unit quads at y=0 for passable kinds), doors
  (closed: a thin box in the doorway; open/doorway: two posts), stairs
  (a lit quad). Rebuild only when the set of known cells changes (keep a
  hash of `kind` per cell). `unexplored` cells are not built: the dark
  fog does the rest.
- Materials: `MeshLambertMaterial` with small procedural
  `CanvasTexture`s generated at start (brick 64×64 with mortar,
  flagstone 64×64, door planks), repeat per cell; colours dark grey stone
  as in the raycaster (`docs/render.md` colour table). A `PointLight`
  attached to the camera (lantern: distance ~8 cells, decay 2) plus a
  faint ambient; `scene.fog = FogExp2(0x000000, 0.25)`.
- Sprites: `THREE.Sprite`s (or camera-facing planes) per `Sprite` with a
  `CanvasTexture` from its `Tile` (16×16, `NearestFilter`, transparent
  index → alpha 0), sized by `Sprite.height`, feet on the floor; cached
  textures by tile name; letters are not drawn here — the style shader
  turns the coloured pixels into glyph density (AsciiCity's whole point).
- Camera: `makeCamera(aspect)`, positioned at the hero's cell centre,
  eye height 0.5, yaw from the fps mode (interpolated as today), vertical
  FOV = the mode's `vFovDeg`; the horizon offset from T-0023
  (`horizonFrac 0.42`) can be approximated with `camera.setViewOffset` or a
  small pitch — pick one and say which.
- `web/src/gl/gl-viewport.ts`: owns renderer/scene/camera/`StyleRenderer`;
  `resize(cols, rows, cellW, cellH)`, `setStyle(id)`, `render(session,
  pose, sprites, nowMs)`. The canvas is absolutely positioned under the
  `<pre>`'s viewport rectangle (T-0030's `DomTerm` exposes the rect and
  cell size); the `<pre>` cells inside that rect are painted transparent
  (space with no bg) by the fps/ortho modes when `gl` is active.
- Style selection: `F5` cycles through AsciiCity's `STYLE_ORDER` in the
  browser (the tty's four themes are a subset), default `amber`; `R`
  is NetHack's key, do not take it.
- Frame loop: `requestAnimationFrame`; render only when the session
  changed, the yaw is animating, or the style has a time uniform.
- Tests (node, no WebGL): `tests/gl-scene.test.ts` covers the pure
  builder — a `ROOM` level yields the expected number of wall cubes and
  floor quads, doors produce posts, incremental refresh rebuilds only when
  a cell kind changes, sprite placement puts feet at y=0 and the centre
  at the cell centre. Everything touching WebGL is thin and reviewed by
  the PM in a browser.
- Manual (PM does the browser run; describe what you could verify):
  `npm run web:server` + `npm run web:dev`, `?name=tester&mode=fps`, the
  scene shows the starting room in amber; `F5` cycles styles; turning
  and walking work.
