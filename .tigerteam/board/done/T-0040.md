## Goal
Make the port visible: assemble renderer + pipeline + dungeon scene +
atmosphere into one `GpuPath`, feed its frame to the AsciiCity style pass (or
straight to the screen in raw mode), and fall back to today's WebGL path when
the GPU path cannot run. After this ticket the browser fps view is rendered by
the ported stack.

## Context
- **The sources are vendored in-repo at `vendor/afterburn/` (read-only).**
  `~/afterburn` itself is **not** visible inside the worker container —
  read the vendored copy, and diff your port against it before you hand
  off. A port written from a description instead of the source is not a
  port (this cost T-0037 an attempt).
- **Read first**: `docs/gpu.md` §6 (composition — the hard rules are there),
  §3 (fallback) and §8 (budget); then `docs/gpu-pipeline.md`,
  `docs/gpu-materials.md`, `docs/gpu-dungeon.md` (landed by T-0037/38/39), and
  `web/src/gl/gl-viewport.ts` as it stands.
- **The composition trick, exactly as specified in `docs/gpu.md` §6.** The
  vendored style shaders are raw GLSL on a `WebGLRenderer` and
  `web/src/asciicity/**` must not be edited. So: the GPU pipeline renders into
  its **own** canvas; `compose.ts` wraps that canvas in a
  `THREE.CanvasTexture` on a full-screen quad in a one-mesh scene and passes
  *that* scene to the untouched `StyleRenderer.render(scene, camera)`. The
  quad's vertex shader writes clip space directly and ignores the camera, so
  pass the **real perspective camera** in — that is how `cameraNear`/
  `cameraFar` stay correct for the styles. Mark the canvas texture
  `needsUpdate` once per frame.
- **Depth styles are a hard rule, not a TODO.** Only `edges` sets
  `needsDepth`. A blitted quad has no scene depth, so while a `needsDepth`
  style is active the viewport renders through the **legacy WebGL path**; it
  returns to the GPU path when the style changes. Implement this as a pure
  exported decision function so it is testable:
  `export function choosePath(opts: { gpuParam: 'auto'|'off'|'raw'; gpuReady: boolean; styleNeedsDepth: boolean }): 'legacy' | 'styled' | 'raw'`.
- **The grade vs. the quantiser — read `docs/gpu.md` §6.1, it is a decided
  contract.** Styled mode must set `look.vignette = 0`, `look.grain = 0` and
  `look.outputScale = 1 / styleExposure` (the `StyleRenderer`'s exposure,
  1.7 by default); raw mode leaves all three at their defaults. If
  `createLook()` has no `outputScale` yet, add it (default `1.0`, applied as
  the last multiply of the grade block beside `fade`) — `web/src/gpu/pipeline.ts`
  is in this ticket's scope for exactly that one addition, and for nothing
  else. Export the pure `styledLook(look, styleExposure)` /
  `rawLook(look)` helpers that apply these and test them.
- **Which mood is active — decided, implement exactly this.** `GpuPath` owns
  an `Atmosphere` and picks the mood from the hero's own cell each frame
  (`level.kindAt` / `cellAt` at `floor(pose.x), floor(pose.y)`), blending with
  `blendTo(id, 1.5)` so a step through a doorway is a fade, not a cut:
  | hero's cell | mood |
  |---|---|
  | `lava`, or orthogonally adjacent to a `lava` cell | `lava` |
  | `ice` | `ice` |
  | `water`, or adjacent to `water` | `flooded` |
  | any cell whose `MapCell.lit === true` | `torchlit` |
  | anything else (corridor, unlit room, unknown) | `deep_dark` |
  Evaluate in that order, first match wins. Export the pure
  `moodFor(level, x, y): MoodId` and test it. Add `?mood=<id>` to pin one
  mood for review — when it is set, the table is bypassed entirely.
- **The lantern and the camera.** The GPU scene needs its own
  `THREE.PerspectiveCamera` and its own lantern: place the camera exactly as
  the legacy path does (`position = (pose.x, EYE_HEIGHT, pose.y)`,
  `rotation = (CAMERA_PITCH, -pose.yaw, 0, 'YXZ')`, `fov = vFovDeg`) and
  parent a `THREE.PointLight` to it using the existing exported
  `LANTERN_INTENSITY` / `LANTERN_DISTANCE` constants from `gl-viewport.ts`.
  Reuse those constants; do not re-invent the numbers. `docs/gpu.md` §3.1 has
  the torch reference (`PointLight(PAL.lamp, 8, 6, 2)`) if the lantern needs
  its own tuning — but that is the tuning ticket's job, not this one.
- **Sizing** (`docs/gpu.md` §6): styled mode renders the GPU canvas at exactly
  the style's scene-target size (`style.cols·subX × style.rows·subY`, already
  capped at 640×360 by `styleGrid`); raw mode renders at the viewport size
  with pixel ratio capped at 1.5. Export the pure
  `gpuCanvasSize(mode, style, cols, rows, viewportPx)` and test it.
- **The bench must get the GPU path for free.** `web/src/scene-bench.ts`
  (`/scene.html`) is the PM's only way to look at this — it constructs
  `new GlViewport({ initialStyle })` and is **not** in this ticket's scope, so
  it must not need editing. Therefore `GlViewportOptions` gains optional
  `gpu`, `quality` and `backend` fields whose **default is parsed from
  `window.location.search`** inside `GlViewport`. `main.ts` may pass them
  explicitly; the bench just works. Put the parsing in a pure exported
  function and test it.
- **Controls and params.** `?gpu=auto|off|raw` (default `auto`),
  `?backend=webgpu|webgl2` (default: whatever the renderer reaches) and
  `?q=low|medium|high|ultra` (default `caps.maxQuality`) and `?mood=<id>`
  parsed in
  `web/src/main.ts` beside the existing `?render=`/`?mode=`/`?theme=`
  handling; **F8** toggles raw ↔ styled at the document level next to the
  existing F5/F2/F3 capture (verify F8 is unbound in `src/ui/app.ts` first —
  F1–F7 are taken; if F8 turns out to be taken, use F9 and say so).
- **Render only from `requestAnimationFrame`** (`docs/gpu.md` §3). On the
  WebGL2 backend, calling `pipeline.render()` in a synchronous loop returns an
  all-black frame once TRAA or DOF is in the graph. `GlViewport.render()` is
  already called from the app's rAF loop, so this is a "do not 'optimise' it
  into a sync loop, and do not conclude the path is broken from one frame"
  warning — the first frames are legitimately empty while TRAA fills its
  history.
- **God rays: do not pass a `sun` unless it casts shadows** (`docs/gpu.md`
  §3). `GodraysNode` reads the light's shadow map and throws on a null one
  while building the graph, killing the whole pipeline. A dungeon normally
  has no sun, and `createPipeline` skips the branch when `sun` is null — so
  pass `null` unless and until the scene grows a real shadow-casting shaft
  light.
- **Backends — measured, read `docs/gpu.md` §3.** On this host headless
  Chromium *reaches* the WebGPU backend but three r185 then throws on a
  `GPUTextureViewDescriptor.swizzle` mismatch, while three's **WebGL2 fallback
  backend renders the same graph fine**. So the fallback is a first-class
  path, not a theoretical one: `?backend=webgl2` must force
  `new WebGPURenderer({ forceWebGL: true })` (same spelling the probe page
  `web/src/gpu-probe.ts` uses), and a first-frame throw on the WebGPU backend
  must retry once on WebGL2 before giving up to the legacy path.
- **Fallback.** If `createRenderer()` throws, `init()` rejects, or the first
  frame throws (after the WebGL2 retry above), log exactly one line
  (`console.warn`) and use the legacy path for the rest of the session.
  The observed WebGPU failure here *does* throw synchronously out of
  `pipeline.render()` (`TypeError: Failed to execute 'createView' …`), so a
  `try/catch` around the first frame is enough to trigger the retry — that is
  measured, not assumed. As cheap insurance for failures that do not throw,
  also fall back when the WebGPU device reports itself gone: on the WebGPU
  backend, `void renderer.backend.device.lost.then(() => …)` and an
  `uncapturederror` listener both route to the same one-line-warn fallback.
  Guard both in a `try` — neither exists on the WebGL2 backend. The browser client must keep working with the
  GPU path dead — that is what `?gpu=off` proves.
- `GlViewport` owns both paths and decides per frame; keep its public API
  (`place`, `resize`, `setStyle`, `setView`, `cycleStyle`, `debugInfo`,
  `render`, `dispose`) unchanged, and keep the ortho view on the legacy path
  for now (`docs/gpu.md` §7). Extend `debugInfo()` with the active path, the
  resolved quality and the backend (`webgpu` vs `webgl2`) — that is the PM's
  only window into what actually ran.
- TS strict, named exports, no `any`, relative imports end in `.js`.
  `tests/gpu-compose.test.ts` runs in node under the root tsconfig (no DOM
  lib): import only the pure functions — keep `choosePath`, `gpuCanvasSize`
  and the param parsing in modules that do not pull in `three/webgpu` or the
  DOM.
