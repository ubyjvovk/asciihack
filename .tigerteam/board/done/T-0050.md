## Goal
T-0043 put the overhead view on the GPU path and its unit tests pass, but the
view renders a **completely black frame**. Unit tests over pure helpers cannot
see that; the PM's eyeball review caught it after the accept. Make the ortho
view actually render.

## Context
- **The sources are vendored in-repo at `vendor/afterburn/` (read-only).**
  `~/afterburn` is not visible inside the worker container.
- Read `docs/gpu.md` §3 and §7, `docs/gpu-ortho.md` (which documents the
  approach that does not work) and `docs/gpu-compose.md`.
- `GpuPath` lives in `web/src/gl/gl-viewport.ts`; `web/src/gpu/ortho.ts` holds
  the pure helpers. `web/src/gpu/pipeline.ts` is in scope **only** for adding
  a way to rebuild the graph against a different camera.
The pure helpers in `web/src/gpu/ortho.ts` are good and the three named tests
are the right ones — keep them. But **the ortho view renders a completely
black frame on the GPU path**, and the unit tests cannot see that, which is
why `docs/gpu.md` §9 says the eyeball review is the PM's.

**Measured just now on the bench** (`/scene.html`, SwiftShader, 1280×720,
`pose=7.5,4.5,90`), max/mean luminance of the frame:

| what | max | mean |
|---|---|---|
| `?gpu=off&view=ortho` (legacy path) | 225 | 3.9 |
| `?gpu=raw&q=low&view=ortho` | **0** | **0.0** |
| `?gpu=raw&q=medium&view=ortho` | **0** | **0.0** |
| `?gpu=raw&q=high&view=ortho` | **0** | **0.0** |
| `?gpu=auto&q=high&render=amber&view=ortho` (styled) | **0** | **0.0** |
| `?gpu=raw&q=high` (fps, for reference) | 252 | 42.6 |

Zero console errors in every case. Note it is black even at `q=low`, which
has no SSGI, no SSR and no DOF — only bloom, FXAA and the grade. So this is
**not** depth-reconstruction in the fancy passes: nothing is being drawn at
all. The scene, the lights and the geometry are fine, because the same scene
renders in fps and through the legacy ortho path.

**The likely cause, and the fix I want.** The current approach copies the
`OrthographicCamera`'s projection matrix onto the `PerspectiveCamera` the
pipeline was built with:

```ts
this.camera.projectionMatrix.copy(this.orthoCamera.projectionMatrix);
```

`pass(scene, camera)` binds that camera **into the node graph at build time**,
and the node system derives its own camera uniforms (projection, inverse,
near/far, and `isPerspectiveCamera`-dependent depth maths) from it. A
hand-copied matrix on a camera that still reports itself as perspective is
not a supported configuration, and anything that calls
`updateProjectionMatrix()` on that camera silently throws the copy away.

So: **stop faking it, and give the graph the real camera.** Rebuild the
pipeline graph against the actual `OrthographicCamera` when the view changes.
`createPipeline`'s `build()` already exists for exactly this (it is what
`setQuality` uses) — extend the handle with a way to rebuild against a
different camera, and call it **only on a view change**, never per frame. A
graph rebuild when the player presses F3 is fine; it is a mode switch, not a
hot path. If you would rather hold two pipelines (one per camera) and switch
between them, that is acceptable too — say which you chose and why.

Whatever you choose, the ortho camera must be a real `OrthographicCamera`
that the graph knows about, so that `isOrthographicCamera` is true where
three checks it.

**Also fix while you are here:** `docs/gpu-ortho.md` currently documents "the
projection copy" as the design. Rewrite that section to describe what you
actually build.

## Rework (attempt 3) — root cause found, this is a small fix

The `debugInfo()` work did exactly its job: the instrument is honest now, and
it hands us the answer. In an ortho GPU frame it reports

```json
"camera":{"type":"ortho","position":{"x":-15.67,"y":23.44,"z":-18.67},
          "target":{"x":7.5,"y":0.5,"z":4.5},"near":0.1,"far":200,
          "left":-4.35,"right":4.35,"top":2.45,"bottom":-2.45},
"meshes":{"walls":8,"floors":8,"sprites":4}
```

The camera is placed correctly, the frustum is sane, the geometry is there.
Keep all of that — `setCamera`, the SSGI→GTAO demotion, the honest
`debugInfo`. The frame is still black for a different reason.

**Root cause: the mood's fog eats the scene.** That camera sits ~40 world
units from its target. The moods carry first-person fog densities
(`torchlit` 0.10, `deep_dark` 0.20, `ice` 0.09) and `FogExp2` survival is
`e^(−density · distance)`:

| distance | density | scene survives |
|---|---|---|
| 6 cells (fps) | 0.10 | 54.9 % |
| 40 units (ortho) | 0.10 | **1.8 %** |
| 40 units (ortho) | 0.01 | 67.0 % |

At 1.8 % of a dungeon that is already dark, against a fog colour of
`0x0b0d10`, every pixel lands under the black point. That is the black
frame — and it is why it was black at **every tier**, including `low`: fog is
applied in the scene pass, before any of the post stack.

The legacy path already solved this and the constants are still sitting in
`web/src/gl/gl-viewport.ts`:

```ts
export const FPS_FOG_DENSITY = 0.10;
export const ORTHO_FOG_DENSITY = 0.01;   // "the ortho camera sits far from
                                         //  the scene, so its fog density
                                         //  must be much lower"
```

**The fix:** when the GPU path is in the ortho view, scale the mood's fog
density by `ORTHO_FOG_DENSITY / FPS_FOG_DENSITY` (= 0.1) rather than using
the mood's value raw, and restore it on the way back to fps. Do it where the
atmosphere writes fog, so a mood blend keeps working and `deep_dark`'s
heavier fog stays proportionally heavier. Reuse the two exported constants —
do not introduce a third number.

Check the DOF focus too while you are there: `orthoDofFocus` already exists
for this, but confirm it is driven by the *actual* camera-to-target distance
now reported in `debugInfo`, not by a first-person default.

### Approach (rework 3)

The reworker's root-cause diagnosis is right: with the camera correctly
placed at ~40 units from its target, `FogExp2` survival `e^(−0.10 · 40) ≈
1.8 %` against `torchlit`'s near-black fog colour (`0x0b0d10`) puts every
pixel under the black point. The legacy path already solved this in T-0032
with two constants living in `gl-viewport.ts`; the GPU path now reuses
them.

**Where the change wires in.** `web/src/gpu/moods.ts` is not in this
ticket's scope, and its `Atmosphere` writes to *its own* private fog
uniforms every `_apply()`. So `GpuPath.create()` **replaces
`scene.fogNode`** — the atmosphere's constructor already set it, we
overwrite it — with a fresh `fog(fogColor, densityFogFactor(fogDensity))`
bound to uniforms `GpuPath` owns. The atmosphere's writes into its
now-orphaned uniforms every frame are harmless; each `GpuPath.render`
frame, after `atmosphere.update(dt)` has run its blend, drives our
uniforms from `atmosphere.state`:

```ts
this.fogColor.value.setHex(currentMood.fog.color);
this.fogDensity.value = moodFogDensityForView(view, currentMood.fog.density);
```

`moodFogDensityForView` is a pure helper in `web/src/gpu/ortho.ts` that
applies `ORTHO_FOG_DENSITY / FPS_FOG_DENSITY` (= 0.1) when `view ===
'ortho'` and returns the density unchanged for fps. It is a
**multiplicative scale**, so `deep_dark`'s heavier fog stays
proportionally heavier than `torchlit`'s — the mood table's expressive
range is preserved for the far camera.

**Constants moved to `web/src/gpu/ortho.ts`.** `FPS_FOG_DENSITY` and
`ORTHO_FOG_DENSITY` used to live in `gl-viewport.ts` (T-0031/T-0032).
`gl-viewport.ts` uses the DOM, so a pure test cannot import from it under
the root tsconfig (`lib: ["ES2022"]`, no DOM). Moved the two constants to
`ortho.ts` and re-exported them from `gl-viewport.ts` for docs/web.md and
any external caller — no behaviour change on the legacy path, but the
helper can now reference the two constants directly (rework 3's "no third
number" requirement) and the pure test can too.

**DOF check (from the reworker's list).** `orthoDofFocus(placement)`
already computes the distance between `placement.position` (the ortho
camera) and `placement.target` (the hero cell) from what
`orthoPlacement` returns — the same numbers `debugInfo()` now reports.
By construction the distance is `ORTHO_DISTANCE_CELLS`; the existing
"DOF focus follows the ortho camera distance" test pins that invariant.
No change needed.
