## Goal
`F3` in the browser shows the same three.js dungeon from a fixed 3/4
overhead camera (the Diablo/Fallout view), rendered through the same
AsciiCity style shaders, with the hero drawn and walls in front of the
hero cut away.

## Context
- `docs/web.md` (T-0031's viewport: `GlViewport` owns renderer / scene /
  camera / `StyleRenderer`; `render(session, pose, sprites, nowMs)`),
  `web/src/asciicity/render/scene.ts` (`makeCamera` is perspective; add an
  orthographic one here, do not edit the vendored file), the terminal
  ortho conventions in `docs/render.md` (north up-right on screen).
- `web/src/gl/ortho-camera.ts` (pure maths + a thin three.js wrapper):
  `THREE.OrthographicCamera` looking at the hero's cell centre from
  azimuth 225° (so north is up-right and east down-right, like the
  terminal ortho) and elevation 35°, `up = +y`; the view height in cells
  is `rows / (3.5 · k)`-equivalent: choose the frustum so the hero sprite
  is about 1/7 of the viewport height (`viewHeight = 7 · heroHeight`
  world units), keep aspect from cols/rows and the cell aspect.
  `placeOrthoCamera(cam, hero, cols, rows, cellAspect)` is the pure part
  (positions/frustum as numbers) so it can be tested without WebGL.
- Hero sprite: in fps the hero is not drawn; in ortho add a `Sprite` for
  the hero at `session.hero` with the tile of the player's role when
  `tiles.json` has it (monster tiles include the player roles:
  `archeologist`, `barbarian`, …, `valkyrie`, `wizard`; the role is the
  last word of the status title before " the ", e.g. "Pmtest the
  Rhizotomist" → look up the rank title is unreliable, so use
  `session.status` `BL_TITLE` only as a fallback and prefer the role from
  `NETHACKOPTIONS` if the client passed one; else a generated `@`
  canvas texture), `height 0.7`.
- Cutaway: wall cubes whose cell is within 2 cells in front of the hero
  (greater `x + y`, `|dx| ≤ 2`, `|dy| ≤ 2` — the terminal rule) use a
  second material instance with `transparent: true, opacity: 0.35`; swap
  materials per frame only when the hero cell changes (cheap: keep the
  set of cutaway cells and rebuild the affected mesh group).
- Nit from the PM's T-0031 check (fix here): pressing `F5` changed the
  style but nothing repainted until the next session event — a style
  change (and a view change) must request a frame immediately.
- `GlViewport.setView('fps' | 'ortho')`; `main.ts` wires `F3`/`F2` to it
  and keeps the minimap/compass rose HUD from the `<pre>` grid.
- Tests: `tests/gl-ortho.test.ts` — `placeOrthoCamera` puts the camera
  north-west-above the hero (x < hero.x, z < hero.y, y > 0), frustum
  height gives the hero ≈ 1/7 of the rows, aspect correct; the cutaway
  set for a hero at (10,10) contains (11,11) and not (8,8) or (14,14).

## Worker report (rework 2)

### Which of the PM's 1-4 was wrong

**None of them caused the black canvas.** I checked each in order:

1. **Frustum** - `placeOrthoCamera` already calls `updateProjectionMatrix()`
   after setting left/right/top/bottom/near/far; top=+2.45 > bottom=-2.45 is
   not inverted; `viewHeight = 7*HERO_SPRITE_HEIGHT` maps to top/bottom and
   left/right by aspect exactly as specified. Not the cause.
2. **Placement** - the position is in world units (x east, z south, y up) at
   distance 40 >= 20 from the hero cell centre, NW-above (azimuth 225deg),
   which satisfies the acceptance test `x < hero.x, z < hero.y, y > 0`.
   Not the cause.
3. **render** - the ortho branch already passes `this.orthoCamera` to
   `StyleRenderer.render(scene, camera)`. Not the cause.
4. **Lighting** - the lantern `PointLight` is a child of the perspective
   camera, parked at the hero cell in both views; the ambient light is never
   removed on view switch. Not the cause.

The real cause is **the scene fog**: `scene.fog = FogExp2(0x000000, 0.10)`.
The ortho camera sits ~40 world units from the scene, and FogExp2 at depth 40
with density 0.10 gives a fog factor of `1 - exp(-(0.10*40)^2) = 0.9999999` -
**every surface is fogged to black**, so the style target (and hence the whole
canvas) is black. fps is fine because the camera sits at the hero cell (depths
1-10, fog factor 1-63%). This matches the observation exactly: same scene,
same materials, same lights - only the camera distance differs.

### Fix

- `web/src/gl/gl-viewport.ts` - made the fog density view-dependent:
  `setView` now switches `scene.fog.density` between `FPS_FOG_DENSITY = 0.10`
  and `ORTHO_FOG_DENSITY = 0.01` (a small value keeps a faint depth cue
  without blacking out the 3/4 view). `FPS_FOG_DENSITY` also replaces the
  hard-coded `0.10` in the constructor.
- `web/src/gl/ortho-camera.ts` - added `ORTHO_NEAR = 0.1` / `ORTHO_FAR = 200`
  and used them in `orthoPlacement` (the PM's item-1 ask; far was 100).
  Placement and frustum geometry were otherwise already correct.
- `web/src/main.ts` - added the debug handle `window.__asciihack = { gl }`
  (in the `gl !== null` branch).
- `web/src/gl/gl-viewport.ts` - added `debugInfo()` returning a plain-number
  snapshot `{ view, camera: { type, position, target, near, far, left, right,
  top, bottom }, meshes: { walls, floors, sprites }, styleId }`, and a
  `lastHeroCell` field to derive the camera `target`.
- `docs/web.md` - updated the "Ortho view" section with the per-view fog rule

### Reviewer note: vendored depth-style limitation (item 3 tail)

The vendored `post.ts` copies `cameraNear`/`cameraFar` into the common
uniforms **only** when the camera is a `PerspectiveCamera`; for the ortho
camera they stay at the defaults 0.3/2000. Per the acceptance criterion

kept so a future in-scope change can adopt it. Flagging so the PM can decide
