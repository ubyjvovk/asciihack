## Goal
The client half of the protocol: spawn `nh-bridge`, parse its JSON lines,
keep the session model (map, hero, messages, status, windows, menus,
pending request) and answer requests — `docs/architecture.md` §4. Every
UI mode is built on this, so it must be exact and well tested against
recorded streams.

## Context
- Read `docs/architecture.md` §3.2–§3.5 and all of §4; the wire types are
  `src/engine/protocol.ts` and the model types `src/model/types.ts` (both
  PM-owned — import them). What the bridge actually does is in
  `docs/bridge.md` (T-0002's report); if it deviates from §3, follow the
  bridge and say so in your report.
- **PM observations from the real bridge (2026-09-03), follow these:**
  - Startup call order: `init_nhwindows` → `create_nhwindow(NHW_MESSAGE)` →
    `status_init` → `create_nhwindow(NHW_MAP)` → `create_nhwindow(NHW_MENU)`
    (the tutorial prompt: items "Yes, do a tutorial" / "No, just start
    play"; `select_menu` follows) → `display_nhwindow` message+map →
    `player_selection` (needs a `ret: 0` reply; with role/race/gender/
    align unset NetHack simply picks at random after it returns — no
    `yn` "Shall I pick" prompt in this port) → `cliparound`/`curs` → status
    updates → `print_glyph`s → `nhgetch`. **No NHW_STATUS window is
    created**; status arrives only through `status_update`.
  - Default `NETHACKOPTIONS` the session must set unless the caller
    overrides: `!tutorial,pettype:none` is NOT wanted (pets are fine) —
    set `!tutorial` only, plus `name:<name>`, and pass `-u <name>`.
  - `status_update` field values are strings except `BL_CONDITION`
    (number) and `BL_FLUSH`/`BL_RESET` (null). The gold field (`BL_GOLD`)
    arrives as `"\G00000F2E:0"` — NetHack's glyph escape `\G` + 8 hex
    digits + `:` + amount; strip the escape and keep the amount (`0`).
    Field indices seen: 0 title, 1–6 STR..CH, 7 align, 9 score(empty),
    10 gold, 11 HP, 12 HPmax, 13 Pw, 14 Pwmax, 17 hunger(empty), 18 AC,
    19 XP/level, 20 `Dlvl:1  `, 22 condition mask — use the `bl` table
    from hello, never hard-code.
  - The bridge's `hello.mg` has `MG_BW_SINK`/`MG_BW_ENGR`/`MG_BW_ICE`
    sharing one bit (alias); a fresh level shows ~40–100 `print_glyph`s
    before the first key request (only seen cells are drawn).
  - `docs/bridge.md` lists every deviation from §3; read it first.
- `src/engine/bridge.ts`: `spawnBridge(opts: {binary, playgroundDir, name,
  options?: string[], argv?: string[], spawn?: typeof child_process.spawn})`
  → `BridgeProcess` with `messages: AsyncIterable<BridgeMsg>` (line-split
  stdout, `JSON.parse`, tolerant of a partial trailing line), `reply(msg:
  RetMsg)`, `kill()`, `exited: Promise<number>`. Sets `NETHACKDIR` and
  `NETHACKOPTIONS` in the child env. Keep it injectable (the spawn function
  is a parameter) so tests feed a fake child.
- `src/engine/glyphs.ts`: `classifyCmap(symIdx, S): CellKind` implementing
  the §4.2 table by `S_*` name; `cellKindOf(info: GlyphInfo, S): CellKind |
  null` (null for non-terrain glyphs); `isTerrainGlyph(info)`.
- `src/engine/session.ts`: `NethackSession` per §4.1 — a `LevelView`
  implementation over an 80×21 `MapCell` array, `hero`, `messages`,
  `status` (by BL index, plus `statusLines(): [string, string]` assembling
  the classic two lines in tty order: line 1 title/STR/DX/CO/IN/WI/CH/
  align/score, line 2 Dlvl/$/HP/Pw/AC/Xp/T/conditions — take the field order
  from the `bl` table and `nethack/win/tty/wintty.c`), `windows`, `pending`
  and `answer()`. `print_glyph` updates the cell per §4.2 rules;
  `clear_nhwindow(WIN_MAP)` resets the map; `curs(WIN_MAP, x, y)` sets
  `hero`; `putstr(WIN_MESSAGE, …)` appends to `messages`; `display_nhwindow
  (WIN_MESSAGE, true)` → `BlockingDisplayRequest{kind:'more'}`. Requests
  carry everything the UI needs (the menu items, the prompt text, the
  yn choices, the text-window lines). `answer()` builds the `RetMsg`
  (§3.3) and clears `pending`; answering when nothing is pending throws.
  Emits `change` after each batch of messages (coalesce: one `change` per
  chunk of stdout, not per line), `request` when `pending` is set, `exit`.
- `scripts/record-bridge.ts`: runs the real bridge like the T-0002 smoke
  but records every stdout line to `tests/fixtures/bridge/<name>.jsonl`
  and the replies it gave as `{"reply": …}` lines in between, for a
  scripted key sequence given on the command line (e.g. `--keys 'hjkl'`
  with ESC/`y` auto-answers for prompts). Record two fixtures: `start.jsonl`
  (startup until the first key request) and `walk.jsonl` (startup + a
  dozen moves + `S` save with confirmation, so an `exit` line is included).
  Fixtures must stay under 1 MB each; strip nothing else.

## Rework (attempt 2)

Excellent work overall — the PM drove a live game through `NethackSession`
(walk, save, exit 0) and the model, classification and status lines are
right. Two things to fix before the UI ticket builds on this:

1. **Game messages never reach `session.messages`.** In the recorded
   fixtures every real game message ("Velkommen rec, welcome to
   NetHack!…", "You see here 2 gold pieces.") arrives as `raw_print`, not
   `putstr(WIN_MESSAGE)`: NetHack's `pline()` (src/pline.c:239) falls back
   to `raw_print` while `iflags.window_inited` is false, and the shim port
   never sets that flag (every real port does in its `init_nhwindows`).
   The bridge will start setting it (ticket T-0012), after which messages
   arrive through `putstr` on the message window — but `raw_print` still
   carries early/late text ("Saving…", errors) and must never be lost.
   Fix: treat `raw_print` and `raw_print_bold` exactly like `putstr` on
   `WIN_MESSAGE` — append to `messages` and emit `message` (bold →
   `attr` ATR_BOLD if you keep attrs; plain string is fine). Keep the
   existing `putstr` path. Test, by name: `raw_print lands in messages`
   (a `raw_print` call followed by a `putstr` on the message window →
   `messages` has both in order and two `message` events fired).

2. **`answer()` can emit `undefined`.** `answer({kind: 'display'} as
   never)` passes the kind check (pending `display` equals `display`) but
   `buildRetMsg` has no `display` case, so `replyFn(undefined)` runs and
   the bridge dies with "reply parse failed". Make `answer()` accept
   `{kind:'display'}` as a synonym of `dismiss` **and** make `buildRetMsg`
   end with `default: throw new Error(...)` so no unknown payload can ever
   reach `replyFn`. Test: `answer rejects an unknown payload kind` (cast
   through `unknown`; expect a throw and no reply sent) and
   `answer accepts display as dismiss`.

Also: `docs/engine.md` — add a short "Where messages come from" note
(raw_print vs putstr, and that the UI should show everything that arrived
since the previous key request). Do not re-record the fixtures.
